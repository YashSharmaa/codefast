# Bug: lines after a "No newline" marker

A hand-edited patch broke a file for me. This is the patch:

```
--- x
+++ y
@@ -1 +1,2 @@
-old
+a
\ No newline at end of file
+b
```

`parse_patch` accepts it, so the new side holds the line `"a"` without `\n` followed by the line `"b\n"`. Applying it to `old\n` gives `ab\n`, which glues two lines into one. A line without `\n` can only be the last line of a text, so this patch is malformed. `parse_patch` should reject it with a parse error at line 7, the `+b` line.

## Interface changes

None. This adds an error case to the patch parser and leaves the rest of the unified diff rules as they are.

## Behaviour

Inside one file patch, a side ends when a `\` line removes the `\n` from a hunk line on that side. A `-` line is on the old side, a `+` line is on the new side, and a context line is on both, so a `\` line after a context line ends both sides. After a side has ended, any later body line on that side is an error: a ` ` or `-` line once the old side has ended, and a ` ` or `+` line once the new side has ended. This holds for the rest of the hunk and for every later hunk of the same file patch. The error is `Error::Parse` with the number of that body line.

The other side may still go on. So `-a`, `\ No newline at end of file`, `+a`, `+b` stays valid, and so does a later hunk that has only lines of the side that has not ended.

Each file patch read by `parse_patches` starts with both sides open. The existing marker errors are unchanged, and every patch that `format_patch` writes for `make_patch` or `reverse_patch` output still parses. The command line shows these errors like any other parse error: `error: line <n>: ...` with exit 2.
