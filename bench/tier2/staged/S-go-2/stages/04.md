# Checking a batch of requests

Our gateway wants to check several requests in one call. Please let `POST /check` take an array.

## Interface changes

```go
// package engine
func (e *Engine) CheckAll(rs []Request) []Decision
```

## What changes

Until now a body that was a JSON array was a bad request. From now on `POST /check` takes either one request object, answered exactly as before, or a JSON array of request objects, a batch. A body that is not one valid JSON value, or that is neither an object nor an array (for example `null`, `"x"` or `5`), is still 400 with `{"error":"bad request"}`.

A batch is answered with a JSON array holding one entry per element, in order. An element that would be a bad request on its own (not an object, `null`, a field of the wrong type, an empty or missing `method` or `path`) is not checked, and its entry is `{"error":"bad request"}`. Every other element is checked and its entry is its decision object, in the same form as a single answer. The status is 429 when at least one checked element was denied, with a `Retry-After` header holding the largest `retry_after` among the denied elements, and 200 otherwise, so an empty array is answered with 200 and `[]`.

The checked elements are checked with one call to `CheckAll`, which decides the requests one after the other in the given order, exactly as that many calls to `Check` would, except that it reads the clock once for the whole call. So an earlier element can use up the tokens a later one needs. `CheckAll` of an empty or nil slice returns an empty slice and need not read the clock. It is safe for concurrent use, and no `Check` or other `CheckAll` runs between its requests.

Example: with the policy `policy one * /x 1/1m`, the body `[{"method":"GET","path":"/x"},{"path":"/x"},{"method":"GET","path":"/x"}]` gives 429, `Retry-After: 60` and `[{"allowed":true,"matched":["one"],"denied":"","retry_after":0,"remaining":0},{"error":"bad request"},{"allowed":false,"matched":["one"],"denied":"one","retry_after":60,"remaining":0}]`.
