# Bug: a query string gets around the policies

With the policy `policy login * /login 5/30s`, a `POST /check` with the body `{"method":"POST","path":"/login?next=/home","ip":"1.2.3.4"}` is answered with `{"allowed":true,"matched":[],"denied":"","retry_after":0,"remaining":-1}`. The `/login` policy does not match, so anyone can get past the limit by adding `?x` to the path. `/log%69n` gets past it the same way. Both should be limited exactly like `/login`, with the answer `{"allowed":true,"matched":["login"],"denied":"","retry_after":0,"remaining":4}` for the first request.

## What changes

`policy.MatchPath` now cleans the path before it compares anything, in two steps:

1. Everything from the first `?` or `#` to the end of the path is removed.
2. Then every `%XX`, where XX are two hexadecimal digits in either case, is replaced by the byte it stands for, except `%2F` and `%2f`, which stay as they are, so an escape never splits a segment. A `%` that is not followed by two hexadecimal digits is kept as it is. The decoded text is not decoded again, so `%2541` becomes `%41`.

The cleaned path is then matched by the existing rules, so a path that is empty after step 1 matches nothing, and `/api/v1?x=/a/b` matches `/api/*` but not `/api/*/*`. Since `Policy.Matches`, the engine, the server and replays all match through `MatchPath`, they all see the cleaned path. Keys and everything else stay the same.

The pattern is used as written. Because a cleaned path never contains `?` or `#` before it is decoded, a PATTERN that contains `?` or `#` is now `bad pattern`.
