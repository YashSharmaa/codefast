# Bug: quoted CSV fields lose their text

Zip codes and ids lose their leading zeros. With this file loaded as `t`

```
zip,id,note
"02134","007",""
```

`SELECT * FROM t` gives the row `(2134, 7, None)` and prints `2134,7,`. A field in quotes is text that the writer meant as text, so the row should be `('02134', '007', '')`. The output has the same problem the other way round: the string `'007'` prints as `007` and the empty string as an empty field, so they read back as `7` and `NULL`.

## What changes

- `Table.from_csv`: a field whose first character is a double quote is a quoted field. It is never converted. Its text, without the surrounding quotes and with `""` read as one quote, stays a `str`, so `""` gives the empty string and not `None`. Unquoted fields are converted exactly as before, and the empty unquoted field is still `None`.
- `Result.to_csv`: a `str` value is now also wrapped in double quotes when it is empty, or when it matches `-?[0-9]+` or `-?[0-9]+\.[0-9]+` (so it would be converted when read back unquoted). So `''` is written as `""` and `'007'` as `"007"`, while the number `7` is still `7`. The other rules stay: `None` is an empty field, booleans are `true` and `false`, and a field with a comma, a double quote, `\r` or `\n` is quoted with inner quotes doubled. The header line follows the same rules.
- Everything else about reading stays as it was: the header row is never converted, blank lines are skipped, and the errors for no header, duplicate names and a wrong field count are the same.
